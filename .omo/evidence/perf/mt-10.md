# MT-10 — the hosted MCP server stops rebuilding its schemas per request

Perf research mid-term wave 1, item 2 of 3. Selection and reasons:
[`midterm-wave-1.md`](./midterm-wave-1.md).

## What changed

`createMcpHandler` calls the server factory **once per request** — for
`server/discover`, for `tools/list`, and for every `tools/call`. Everything
`createServer` built was therefore rebuilt on each one: 22 tool definitions
with 66 inline `z.object(...)` literals between them, plus three shared
schemas declared inside the function.

None of those definitions close over anything request-scoped. Only the
handlers touch `principal` and `store`. So all 22 definition objects and the
three shared schemas are now module-scope constants, and the per-request work
is the handler closure binding alone.

Nothing else moved: the same `McpServer` is still constructed per request, the
same tools are registered on it in the same order, and the handlers are still
built per request because they must be.
(`packages/mcp/src/hosted.ts`)

## Measurement

Script added for this item: `scripts/bench-mcp-request.ts`.

```
node --import tsx scripts/bench-mcp-request.ts --requests 100
```

Host:

| | |
| --- | --- |
| CPU | AMD Ryzen 7 9800X3D, 8C/16T |
| RAM | 61.6 GB |
| Node | v24.14.0 |
| OS | Windows 11 (10.0.26200) |

Method: the store is `InMemoryMcpStore` over a two-artifact fixture, so the
*answer* to each request is nearly free and what remains is the plumbing.
Requests are posted as raw JSON-RPC straight into `endpoint.fetch` — no
socket, no TLS, no network. They are **not** sent through an SDK `Client`:
its response cache absorbs a repeated `tools/list` without ever reaching the
server, which would have made the number meaningless. The request shape was
captured from `StreamableHTTPClientTransport` so it is what a real client
sends. 20 warm-up requests, then 100 measured; three runs per revision, and
the table quotes the **median of the three runs** for each statistic.

| method | statistic | before | after |
| --- | --- | ---: | ---: |
| `server/discover` | p50 | 3.525 ms | 1.716 ms |
| | p95 | 9.951 ms | 3.217 ms |
| | mean | 4.584 ms | 1.978 ms |
| `tools/list` | p50 | 4.497 ms | 2.637 ms |
| | p95 | 10.093 ms | 3.801 ms |
| | mean | 5.579 ms | 2.703 ms |
| `tools/call` (`search_index`) | p50 | 3.242 ms | 1.415 ms |
| | p95 | 9.521 ms | 2.090 ms |
| | mean | 4.348 ms | 1.542 ms |

The p95 improvement is larger than the p50 one because the removed work was
allocation-heavy, so it also drove the garbage collection that produced the
tail.

### Where the cost was, and what is left

A separate throwaway probe on the same host, over 44 schemas of the shape this
file registers:

| operation | cost |
| --- | --- |
| building 44 `z.object` schemas | 7.287 ms |
| `new McpServer` + 22 `registerTool` | 2.041 ms |
| `new McpServer` alone | 0.004 ms |

Schema construction was the dominant term and is now gone. The ~2 ms of
`registerTool` remains per request, and this change does not touch it. The
report suggests removing it too, by pre-computing JSON Schema and registering
through the SDK's `fromJsonSchema`. That is **not** done here: `fromJsonSchema`
is typed `<T = unknown>`, so every one of the 22 handlers would lose the
argument types it is currently checked against. Trading static type safety on
the whole tool surface for ~2 ms is the wrong trade to make silently — it is
recorded as OQ-024 instead.

## Tests

`packages/mcp/src/hosted.test.ts` gains one case: two tenants served from one
process, listing tools three times across two principals, must see byte-equal
tool catalogs. Hoisting makes those definition objects shared, so if the SDK
ever mutated one during registration the second server would drift from the
first — this is the assertion that catches it. The existing contract tests
(deterministic tool order, per-tenant isolation, cache hints, scope
enforcement) are unchanged and still pass.

## Guardrails

No session or cross-request state is introduced. The definitions are
constants, not caches: nothing is keyed by principal, nothing survives a
request that did not exist before it. The MCP 2026-07-28 stateless rule is
untouched.

## Assumptions and limits

- Timings are wall clock on one host; only the before/after pairing is
  meaningful.
- The in-memory store makes these numbers the *plumbing* cost. Against the
  production Supabase store the query time is added on top; it is not removed
  by this change and is MT-5's subject.
- The probe table above uses synthetic schemas of similar shape, not the real
  ones. It is a diagnostic for *where* the cost sits, not a measurement of
  this codebase, and no claim in the summary rests on it alone.
