### The pre-existing red is fixed, not excepted

`tests/e2e/release-hardening.spec.ts:8` — "fresh user completes the seeded demo
repository journey" — expected `h1 = specproof/drifted-demo` after the seeded
demo onboarding and had been failing since before this phase.

The Wave 3 handoff attributed it to `a16acaa`; that is wrong. Tracing the
element through history:

| commit | dashboard `<h1>` |
| --- | --- |
| `0f00bfb` → `a16acaa` → `7ed6106` | `{model.repo}` |
| **`e0057dc`** feat(web): rebrand homepage as Arr | `Project proof map` ← broke here |
| `3b96d17` → `1fc9433` | `{DASHBOARD.title}` |

`e0057dc` (pre-Phase-2A) removed the connected-repo identity from the page
heading, which left every workspace with an identical `h1` and put two e2e
specs in direct conflict over the same element — `app-shell.spec.ts:11` wants
`DASHBOARD.title`, `release-hardening.spec.ts:8` wants the repo.

Fixed by option (a) from the handoff: the heading now carries both.

```tsx
<h1 id="proof-map-title">
  {DASHBOARD.title}
  <span className="arr-proof-repo">{model.repo}</span>
</h1>
```

`model.repo` was already in the view model and already rendered in the repo
rail, so nothing new is computed or fetched — this restores information the
heading used to carry. Playwright's `getByRole(…, { name })` matches by
substring, so both specs are satisfied by the real accessible name. **No
assertion was deleted, relaxed, or rewritten.**

### The flake is fixed at its cause, not papered over with a timeout

`tests/e2e/live-graph.spec.ts:37` was reported as a cold-start flake whose
`/graph` step outran the dev server's first compile.

Two separate defects were underneath it:

1. **The compile race.** `tests/e2e/global-setup.ts` now requests every route
   the suite touches, sequentially, before any worker starts. Next compiles them
   once; every worker afterwards hits a warm route. No timeout was raised.
2. **A hydration race the warm server then exposed.** These screens are
   server-rendered, so their controls are visible, enabled and clickable *before*
   React attaches listeners — an interaction landing in that window is accepted
   by the DOM and silently discarded when React commits. That is what made
   `check()` on the orphan toggle and `fill()` on the force slider intermittent
   no-ops (the assertion then saw the pre-interaction value for its full 5s
   timeout). Interactions now wait for a definite hydration signal: the Pixi
   `<canvas>` that only the `dynamic(ssr:false)` renderer can create, and a
   `hydrated()` helper that waits for React's `__reactFiber$…` tag on the host
   node.

Confirmed with `--repeat-each=6` on the previously flaky cases: 6/6.
